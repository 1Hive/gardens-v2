# Shared strategy and community routing

Each CVStrategy and RegistryCommunity remains an ERC1967 proxy with its own state and owner. After migration, its implementation slot points to a family router. The router reads the core implementation and selector-to-facet mapping from the same RegistryFactory used to create new instances. Router UUPS upgrades retain `ProxyOwnableUpgrader` owner authorization.

## Release calls

- `setStrategyImplementation(newCore)` is one owner transaction for a core-only strategy release. `setCommunityImplementation(newCore)` does the same for communities.
- `setStrategyRelease(completeCuts, newCore)` is one owner transaction for a strategy release changing core and/or facets. `setCommunityRelease` is the community equivalent. These replace the complete selector set atomically; include every selector that should remain callable.
- `setStrategyFacets` and `setCommunityFacets` still replace the complete facet set and sync routing in one call. Once shared routing is active, the split `clear*FacetCuts` and `upsert*FacetCut` methods revert, because intermediate transactions would expose incomplete routing.
- A change that adds or changes per-instance state also needs an explicit, separately authorized `runImplementationMigration(data)` call on every affected proxy. A factory write cannot initialize individual proxy storage.

New routed strategies execute the factory's configured `strategyInit` and `strategyInitCalldata` during proxy construction, after the core's `init` state setup. The router's factory must match the creating community's factory. Existing strategies do not rerun this initializer when they migrate to a router.

The factory validates code-bearing implementation and facet targets, duplicate/reserved selectors, and that routed templates point back to this factory. Its owner controls shared releases. Existing proxy owners control migration and router UUPS upgrades. Owner permissions must be checked on the actual chain before preparing a release.

## Initial migration

1. Build and audit the new RegistryFactory implementation, both routers, current CVStrategy and RegistryCommunity core implementations, and the new CommunityPoolFacet. Verify storage layouts and run the contract suite. Upgrade the factory proxy using its existing governed owner flow. Do not change its templates yet.
2. Deploy the two routers with the factory proxy address in each constructor. Deploy the core implementations and CommunityPoolFacet. Check code hashes, UUPS UUIDs, owner resolution, and the routers' `routingFactory()` values.
3. Run `node scripts/prepare-shared-routing.mjs --help`, then use `task prepare-shared-routing` with `PHASE=activate`, the target `NETWORK`, `RPC_URL`, deployed `STRATEGY_ROUTER`, `COMMUNITY_ROUTER`, `STRATEGY_LOGIC`, `COMMUNITY_LOGIC`, `COMMUNITY_POOL_FACET`, and a fresh empty `OUT` directory. It derives the direct executor from the local Foundry `PK_DEPLOYER` keystore with `PK_DEPLOYER_PW`; optional `MIGRATION_EXECUTOR` must match the derived address. Set `SAFE_ADDRESS` instead only when the Safe is already the effective owner. The script checks code, factory wiring, the effective owner, and the factory community nonce against the configured community count. It never submits transactions. Direct owner files set `meta.createdFromOwnerAddress`; they are **not Safe proposals**.
4. Rehearse and execute the `activate` file in order: `setCommunityRelease`, `setStrategyRelease`, then `setRegistryCommunityTemplate(communityRouter)`. The last call makes every subsequently created community routed. Record its successful transaction hash. If only some calls execute, regenerate `activate`; it emits the missing calls and rejects a conflicting core or facet.
5. Run `task sync-proxies NETWORK=<chain>` after the subgraph has indexed the community template switch. Generate `PHASE=communities` with `SUBGRAPH_URL` and `SWITCH_TX` set to that template switch transaction hash. The generator verifies the successful factory event, waits for the indexed block to reach the receipt block, and requires the indexed proxy sets to equal `networks.json`. Rehearse and execute all community batches; repeat sync and generation until no community proxy remains direct. The factory nonce catches communities absent from the configured list.
6. Generate and rehearse `PHASE=switch-strategy`; it refuses to switch while any configured community remains direct. Execute `setStrategyTemplate(strategyRouter)` and record its successful transaction hash. From then on, newly created strategies are routed. Sync proxies again after the subgraph indexes this transaction. Generate `PHASE=strategies` with that hash and the subgraph URL; the generator requires the indexed strategy set to match config, then emits only direct strategies. Rehearse and execute the batches, repeat sync and generation, and run `PHASE=verify` until its manifest reports zero pending instances and no transactions. Check implementation slots, ownership, state, pause behavior, and representative facet calls after each batch.
7. Once every proxy and template is verified as routed, have the current upgrade wallet call `renounceUpgradeAccess()` on that chain's live ProxyOwner proxy. Confirm `upgradeAccess()` is zero and `owner()` on the factory and all configured proxies resolves to the governance Safe. Only then use the Safe release flow below. Recheck the actual ProxyOwner, wallet, and Safe addresses on each chain; the Base configuration alone does not establish them elsewhere.

On Base, the currently observed upgrade wallet is `0x00BcC26E792E393217bA895f5e85AE628FC994E9` and the governance Safe is `0x9a17De1f0caD0c592F656410997E4B685d339029`. The Base ProxyOwner proxy is `0x99EBeF5E196a9e8e39d92B18663C9236661607b1`; `0x6da32bb79a32797a33cf00cfacd0870162140d0a` is its implementation. Verify these values again immediately before live execution.

The ordering matters: old communities must receive the new CommunityPoolFacet before the strategy template switches. The old pool creation facet tries to make a local `diamondCut`, which a router intentionally rejects. A single payload prepared before migration cannot safely enumerate instances created during its own execution; prepare and verify each phase against fresh chain and subgraph state.

Current `UpgradeCVMultichain` and split facet upgrade scripts describe the older per-instance release flow. Use the shared release calls for routed instances, and do not run a legacy script that upgrades instances away from the routers.

## Deployment and later releases

- `DeployCoreContracts` phase 2 installs both routers and activates both factory releases for a **new** factory. It refuses to rerun phase 2 once shared routing is active. Its phase 1 factory and core implementation addresses are used directly when `all` runs in one script invocation.
- For an existing factory, `DeploySharedRoutingTargets` with `SHARED_TARGET_MODE=migration` deploys the candidate factory implementation, both routers, both cores, and CommunityPoolFacet. `task deploy-shared-routing-targets` wraps it using `NETWORK`, `RPC_URL`, and `PK_DEPLOYER_PW`. It verifies the RPC chain ID and configured chain-local `CV_UTIL_LIB`, compiles through IR so CVStrategy fits the 24,576-byte runtime limit, and broadcasts the six creations sequentially. It prints the candidate addresses and does not update the active network config or upgrade the factory. Upgrade the factory through the governed flow, then use `prepare-shared-routing.mjs` to create the phased migration payloads.
- Invoke the deployment task with shell environment variables, for example `NETWORK=base RPC_URL=https://mainnet.base.org SHARED_TARGET_MODE=migration task deploy-shared-routing-targets` from `pkg/contracts`. The task loads `PK_DEPLOYER_PW` from `.env` and passes it to Foundry through a temporary password file.
- After migration, `DeploySharedRoutingTargets` with `SHARED_TARGET_MODE=release` and `SHARED_TARGET_FAMILY=strategy` or `community` deploys a new core implementation. `task refresh-facets-<chain>` can deploy changed facets. Its sync step detects an active shared release and prints the deployed candidates without changing active `.FACETS` in `networks.json`. These deployment steps do not activate a release. Keep candidate addresses separate from the active config until the Safe transaction executes.
- `node scripts/prepare-shared-release.mjs --network <name> --rpc <url> --family strategy|community --safe <effective-owner-safe> --out <file> [--implementation <new-core> --storage-reviewed] [--facet <old-address>:<new-address> ...]` reads the live complete selector set and prepares one `setStrategyRelease` or `setCommunityRelease` Safe transaction. Both core and facet changes for one family belong in that single factory call. The payload includes `meta.createdFromSafeAddress`, so `PAYLOAD_FILE=<file> task rehearse-safe-payload-chain CHAIN=<chain>` can replay it on a fork.
- A router code change is separate from the factory's core and facet release. Pass `--router <new-router> --out <directory> --storage-reviewed` to the same generator. It writes ordered payloads for the optional factory release, the factory template switch, and batched `upgradeTo(newRouter)` calls for every configured instance. The template switch affects new instances; existing instances need their own UUPS writes. Rehearse all stages in order on one fork with `bash scripts/rehearse-safe-payload.sh <chain> <ordered-payload-files...>` before submitting them in the same order. `task prepare-shared-release` wraps this with `NETWORK`, `RPC_URL`, `FAMILY`, `SAFE_ADDRESS`, `OUT`, optional `NEW_IMPLEMENTATION`, `NEW_ROUTER`, `BATCH_SIZE`, `STORAGE_REVIEWED=true`, and space-separated `FACET_REPLACEMENTS`.
- If a new core needs per-instance state initialization, provide each required call as `--migration <proxy>:<initializer-calldata>` and use an output directory. The generator places `runImplementationMigration(data)` calls after the factory release and before any router template switch. The Taskfile accepts the same entries as space-separated `MIGRATIONS`. Identify every affected proxy and construct its calldata from the initializer ABI; an omitted instance remains unmigrated.
- The generator requires the factory effective owner to be the supplied Safe, validates that the Safe has a threshold, and checks each configured proxy owner before preparing router upgrades. It checks current router slots and candidate wiring but cannot establish that `networks.json` includes every live proxy. Reconcile the inventory with creation events before relying on the result.
- `--storage-reviewed` records an operator assertion; it does not compare layouts. Review the deployed old and candidate core/router storage layouts, linked libraries, per-instance migration needs, and exact payload simulation before signing. Account for the interval between release and state migration when the operations span Safe transactions.
- `scripts/verify-all-deployments.sh` selects `verify-shared-routing.mjs` for routed factories. This checks live router wiring, factory selector mappings, core and facet code presence, and the implementation slot of every configured proxy. It does not establish that `networks.json` includes every live proxy or that candidate bytecode matches a local artifact.
- The Taskfile's `verify-diamond-facets-<chain>` aliases now call the router-aware `verify-all-deployments.sh --scope facets` path. On unmigrated chains this still uses the local diamond facet verifier. Verify candidate facet bytecode separately before proposing a release; this task checks the active deployment.
- After each executed migration phase or release, reconcile `config/networks.json` with the live factory: `.IMPLEMENTATIONS.CV_STRATEGY` and `.IMPLEMENTATIONS.REGISTRY_COMMUNITY` are the active cores, and `.IMPLEMENTATIONS.CV_STRATEGY_ROUTER` and `.IMPLEMENTATIONS.REGISTRY_COMMUNITY_ROUTER` are the router templates. Keep `.FACETS` aligned with the live complete cut sets. `VerifyNetworkConfigState` checks these values and requires routed implementation slots once shared routing is active.
- The old `UpgradeCVMultichain`, diamond upgrade, and individual facet replacement scripts remain for chains that have not migrated. They reject a factory or proxy using shared routing. The unused `GenerateFacetUpgradePayloads` script was removed; use `prepare-shared-release.mjs` after migration.
- The Taskfile's legacy `upgrade-<chain>` and fork rehearsal commands check factory routing before syncing proxies or deploying facets. Once a shared release is active, use `task prepare-shared-release` and `rehearse-safe-payload-chain` instead. Legacy scripts remain available for chains awaiting migration.

## Gas and deployment gates

The local warm-read benchmark in `SharedImplementationRouter.t.sol` measured a direct proxy core read at 888 gas and a routed proxy core read at 6,432 gas, a 5,544 gas increase inside the test. Cold transactions, facet calls, writes, and pool creation need separate estimates on the target chain before quoting USD costs.

Run `scripts/verify-storage-layout.sh` against the final build before submitting migration transactions. An earlier version of the checker cached facet layouts by the facet's own source hash and missed changes to inherited base storage; it falsely reported five `_reentrancyLocked` mismatches. The checker now inspects fresh compiled layouts, and all CVStrategy facets match the core at slot 136, offset 1. The generator also requires a fresh live proxy inventory and transaction simulation; it cannot establish either by itself.

# Gardens shared-router upgrade

Use this for a routed CVStrategy or RegistryCommunity core, facet, router, or per-instance state upgrade. Work from `pkg/contracts` unless a command says otherwise. Read `pkg/contracts/docs/shared-routing.md` and `pkg/contracts/AGENTS.md` for the current architecture and chain conventions. If the factory has not migrated to shared routing, follow the initial migration section of that document instead of using a routed release payload.

## Resolve the executor on every target chain

Before generating payloads, read that chain's `name`, `chainId`, `ENVS.PROXY_OWNER`, and `PROXIES.REGISTRY_FACTORY` from `pkg/contracts/config/networks.json`. Confirm the RPC chain ID and nonempty bytecode at `ENVS.PROXY_OWNER`, then call `upgradeAccess()(address)`, `owner()(address)`, and `mainOwner()(address)` on **that ProxyOwner contract**. `ENVS.PROXY_OWNER` is a contract address; compare its resolved `upgradeAccess()` and `owner()` values with the wallet, not the contract address itself. Derive the current `PK_DEPLOYER` address by unlocking its Foundry keystore with `PK_DEPLOYER_PW` without printing the key or password. Also read `owner()(address)` on the configured factory and every proxy targeted by the upgrade.

Use the address book for each chain and read the matching RPC; never reuse another chain's ProxyOwner address:

```bash
jq -r '.networks[] | [.name, .chainId, .ENVS.PROXY_OWNER, .PROXIES.REGISTRY_FACTORY] | @tsv' config/networks.json
cast chain-id --rpc-url "$RPC_URL"
cast code "$PROXY_OWNER" --rpc-url "$RPC_URL"
cast call "$PROXY_OWNER" 'upgradeAccess()(address)' --rpc-url "$RPC_URL"
cast call "$PROXY_OWNER" 'owner()(address)' --rpc-url "$RPC_URL"
cast call "$PROXY_OWNER" 'mainOwner()(address)' --rpc-url "$RPC_URL"
cast call "$FACTORY" 'owner()(address)' --rpc-url "$RPC_URL"
```

- **Direct PK_DEPLOYER path:** `upgradeAccess()`, ProxyOwner `owner()`, factory `owner()`, and every targeted proxy `owner()` all equal the derived `PK_DEPLOYER` address. Check each chain separately and recheck immediately before execution.
- **Safe payload path:** if the direct condition fails, resolve `mainOwner()` on that chain's ProxyOwner, prove it is a Safe contract with a positive threshold, and confirm the factory and every targeted proxy resolve `owner()` to that Safe. Use that resolved Safe in payload metadata and submission. If neither path passes, stop; do not assume an EOA `mainOwner()` is a Safe.

If ownership differs within a batch, split or resolve the batch before preparing transactions. A configured address, a keystore file, or an earlier authorization check is insufficient. Never submit direct-owner files to the Safe Transaction Service.

## Fund the deployer for an authorized upgrade

When the user has requested an upgrade and the resolved direct executor lacks native gas, inspect the **same PK_DEPLOYER wallet's** native and token balances across available chains before asking the user to add funds. The user authorizes using that wallet's existing assets to fund the requested upgrade, including a swap or bridge when needed, **without a separate approval for those funding transactions**. This authorization is limited to the funding needed for the requested upgrade; it does not approve the release payloads or allow spending another wallet's assets.

Choose a supported route from live quotes and verified chain and token addresses. Prefer a same-chain swap when it supplies the needed gas. For a cross-chain route, account for source gas, bridge fees, destination gas, slippage, and arrival time. Spend only enough for the estimated upgrade gas plus a reasonable price buffer, preserve enough source-chain gas to finish the route, and avoid sweeping unrelated balances. Before signing, verify the swap or bridge target, spender, recipient (the same deployer address), chain IDs, minimum output, and allowance; use the smallest necessary allowance. Check simulation where supported, then check each receipt and the destination balance before continuing deployment. If no credible route or sufficient source gas exists, explain the shortfall and ask the user to fund it. Never expose keys, passwords, or private RPC URLs.

## Prepare and prove the candidate

1. Identify the target chain, family, exact source diff, deployed candidate addresses, and expected new behavior. Read live factory/template/implementation/selector state, chain-local linked libraries, and effective owners. Record newly deployed, receipt-verified targets under that chain's `CANDIDATES` in `config/networks.json`; keep `IMPLEMENTATIONS` and `FACETS` as the active onchain addresses until execution. For **initial migration, router upgrades, or per-instance state migrations**, run `task sync-proxies NETWORK=<chain>` from `pkg/contracts` for each target chain (`task sync-proxies-all` for all supported chains). Check every chain's exit status and review the `config/networks.json` diff for added, removed, or changed proxies. A failed multi-chain run may already have written successful chains; resolve unavailable subgraph deployments before preparing affected payloads. Reconcile the synced inventory with live creation events and the subgraph's indexed block; the sync queries at most 1,000 entities per type, so a truncated or lagging result is incomplete. A missing proxy makes per-instance upgrades or migrations incomplete. A **core/facet-only factory release after migration** needs no proxy sync because existing routed proxies read the factory release on each call. Do not treat a local build, subgraph sync, or old payload as proof of deployed code.

   When `ConvictionsUtils` changes, deploy its candidate library separately on **each chain first**. `CVStrategy`, `CVAllocationFacet`, `CVPowerFacet`, `CVProposalFacet`, and `CVStreamingFacet` can have chain-local link references; deploy each affected core/facet with `CANDIDATE_CV_UTIL_LIB=<new-address>`. Inspect the final artifact link references for every deployed contract because inherited functions can add a library link. `task deploy-shared-routing-targets` accepts this override for core releases. `task deploy-remediation-facet` accepts `NETWORK`, `RPC_URL`, `PK_DEPLOYER_PW`, `REFRESH_FACET_KEY=.FACETS.<key>`, and the override for one inactive facet. Without the override, the shared-target task links the active library from `IMPLEMENTATIONS.CV_UTIL_LIB`. Never promote the candidate library into `IMPLEMENTATIONS` before the corresponding release executes.

   For each creation transaction, run `node scripts/verify-remediation-candidate.mjs --network <chain> --rpc <rpc> --contract <contract> --address <candidate> --tx <creation-hash> [--library <new-ConvictionsUtils>] [--power-library <existing-PowerManagementUtils>] --record true` from `pkg/contracts`. It checks the receipt, chain ID, exact compiled runtime, and embedded library links, then records the address in `CANDIDATES` and a receipt/code-hash manifest under `transaction-builder/remediation-candidates/`. `CVPowerFacet` can link both libraries; resolve its existing chain-local `PowerManagementUtils` from the active facet's runtime and confirm it has code. Build with the same compiler flags used for deployment before verifying. For a StreamingEscrow implementation-only candidate, set `DEPLOY_ONLY=true UPGRADE_FACTORY=false SKIP_NETWORK_WRITES=true` when running `DeployOrUpgradeStreamingEscrows`; its default path stages active config writes. Confirm it created only the intended implementation and did not activate the factory or any escrow.

   For this advisory batch, `bash scripts/deploy-remediation-candidates.sh <chain>` performs the ordered inactive deployments, live direct-owner check, receipt/runtime verification, and candidate recording. It resumes from candidates already recorded in the manifest. Supply the chain RPC variables and `PK_DEPLOYER_PW` in the environment. Ethereum Sepolia's state-creation gas repricing may need `SHARED_GAS_ESTIMATE_MULTIPLIER` and `REMEDIATION_GAS_ESTIMATE_MULTIPLIER` set higher; verify each receipt rather than assuming an estimate proves a deployment. The script never switches a factory or proxy.

   If the chain's subgraph deployment is unavailable, use the explicit event-backed path: `PROXY_SOURCE=events PROXY_EVENTS_RPC_URL=<chain-rpc> task sync-proxies NETWORK=<chain>` with `ETHERSCAN_API_KEY` set. This checks the factory's creation and `CommunityCreated` events, each community's `PoolCreated` events, the factory nonce, and recent chain RPC logs for index lag. Check the saved diff. For initial migration payloads set `INVENTORY_SOURCE=events` and the confirmed `SWITCH_TX`; the generator requires the exact switch event to be indexed. Re-run this sync just before executing each proxy batch.
2. Make the relevant unit and upgrade tests pass. Run the full non-fork contract suite, which includes SecurityPoC, and the advisory coverage check from the repo root:

   ```bash
   node pkg/contracts/scripts/check-security-poc-coverage.mjs
   forge test --no-match-path 'pkg/contracts/test/fork/*' --summary
   ```

   Run focused `SharedImplementationRouter.t.sol`, `RegistryFactory.t.sol`, and affected contract tests when those paths are involved. Fix failures before proceeding. For each proposed release, add or update a **next-upgrade test** that applies the candidate release to existing proxies and proves the new version is active through a candidate-specific observable result: a version value, new selector/behavior, or runtime code hash. Assert previous per-instance state and ownership survive. For a router change, also assert each upgraded proxy's ERC1967 slot points to the new router and new instances use the new template. Merely checking the factory's new address is insufficient.
3. Run `bash scripts/verify-storage-layout.sh` from `pkg/contracts`. This checks facet/core alignment and RegistryFactory invariants; it does **not** compare the deployed old implementation with the candidate. Review that old-to-new layout separately, including inherited fields, gaps, router storage, and any required per-proxy `runImplementationMigration(data)` calls. Stop if compatibility or migration order is unresolved.

## Rehearse the exact transaction sequence

4. Generate draft transaction files with `task prepare-shared-release` (`NETWORK`, `RPC_URL`, `FAMILY`, `OUT`, and candidate variables). Set `SAFE_ADDRESS` only for the Safe path; otherwise the task derives the direct executor from `PK_DEPLOYER` and `PK_DEPLOYER_PW`. Use `NEW_IMPLEMENTATION` and `FACET_REPLACEMENTS` for a factory release; use `NEW_ROUTER` for the template switch and per-proxy UUPS batches; use `MIGRATIONS` for per-proxy state calls. Set `STORAGE_REVIEWED=true` only after the layout review. The output is one factory transaction for a core/facet release, or ordered files when router or state migration steps are needed. The generator requires an empty output directory for staged files. For initial migration, use `task prepare-shared-routing` one phase at a time (`PHASE=activate`, `communities`, `switch-strategy`, `strategies`, `verify`). Set `SAFE_ADDRESS` for the Safe path; otherwise it derives the direct owner from the Foundry `PK_DEPLOYER` keystore using `PK_DEPLOYER_PW`, and optional `MIGRATION_EXECUTOR` must match. `communities`, `strategies`, and `verify` require the confirmed preceding template `SWITCH_TX` and either `SUBGRAPH_URL` or `INVENTORY_SOURCE=events` with an Etherscan API key. After each template switch, sync proxies only once the chosen index has the switch event. Direct-owner output is ordered transaction data, not a Safe proposal. See `pkg/contracts/docs/shared-routing.md` for phase order.

   If a replacement facet adds external functions, pass each new selector through `SELECTOR_ADDITIONS="<new-facet-address>:<bytes4> ..."` (or repeated `--selector` with the generator). Derive bytes4 from the exact compiled ABI, confirm it is absent from the live selector set, and verify the new function through an existing proxy in the fork rehearsal. For a StreamingEscrow template and existing-instance upgrade, use `node scripts/prepare-streaming-escrow-release.mjs --network <chain> --rpc <rpc> --implementation <candidate> --executor <resolved-PK_DEPLOYER> --out <file>` or its `--safe <resolved-safe>` path. It enumerates the factory's escrows and writes the template switch followed by one `upgradeTo` per instance; for escrows still using the old slot-105 storage layout, it inserts `reinitializeV2Migrate()` immediately after that instance's upgrade. Recheck the inventory and storage layouts before live execution. For this advisory batch, `bash scripts/prepare-remediation-release.sh <chain>` derives the signer from `PK_DEPLOYER`, prepares the strategy and community releases with the two new dispute selectors, and prepares the escrow payload when supported.
5. Rehearse **the generated files in order** on a fork using `KEEP_ANVIL=true bash scripts/rehearse-safe-payload.sh <chain> <ordered-payload-files...>`. Run the relevant fork lifecycle and candidate-specific next-upgrade test against that modified local fork, then stop the Anvil instance. For this advisory batch, `bash scripts/rehearse-remediation-release.sh <chain>` starts a disposable fork, applies the ordered direct-owner files, and runs `verify-remediation-release-fork.mjs` against the live baseline. It checks candidate cores, old and new selector routing, representative strategy/community state, every escrow's identity fields and implementation slot, and any legacy escrow migration. The general lifecycle smoke suite can compare the post-release fork with the still-active address book and fail on that expected mismatch; use the candidate-specific assertions for the release state. Prove the expected candidate behavior on existing proxies, new creation when applicable, selector routing, storage continuity, and ownership. Stop and revise the candidate or payload if any assertion fails; then repeat preparation and rehearsal. Do not use the legacy `rehearse-upgrade-chain` flow on routed chains because it executes the old per-instance upgrade script.
6. Review the final payloads after rehearsal: chain ID, executor mode and address, factory/proxy targets, full selector sets, implementation/router addresses, ordering, transaction count, linked-library bytecode, and any state migration calldata. Record SHA-256 hashes of the exact files reviewed. For initial migration, router upgrades, or per-instance migrations, re-run proxy sync and live creation-event reconciliation immediately before execution or submission; regenerate and rehearse if the inventory changed. For every release, re-read relevant live ownership and authorization; for Safe payloads, also re-read the Safe nonce/pending queue. Regenerate and rehearse if that state changed. Use `scripts/verify-shared-routing.mjs` or `scripts/verify-all-deployments.sh` as appropriate for current-state checks.

## Direct PK_DEPLOYER path

Use this path only when the chain's `ENVS.PROXY_OWNER` resolves `upgradeAccess()` and `owner()` to the unlocked `PK_DEPLOYER` address and every targeted effective owner matches it. Present the exact ordered direct-owner files, hashes, target chain, transaction count, and expected effect to the user, and obtain approval for those live transactions. Recheck authorization and file hashes immediately before execution. Execute the approved transactions in order with `PK_DEPLOYER`, checking each receipt and the expected state before proceeding to the next stage. Stop if authorization, inventory, or expected state changes. These files set `meta.createdFromOwnerAddress`; they are not Safe proposals and must not be submitted to the Safe Transaction Service. Never expose the key or password.

## Safe payload path

Use the Safe resolved from `mainOwner()` on that chain's `ENVS.PROXY_OWNER`. The expected governance Safe on the configured mainnets is `0x9a17De1f0caD0c592F656410997E4B685d339029`; verify this expectation against live state rather than applying it to testnets. Confirm that the Safe is the effective factory/proxy owner for every payload, that payload metadata names it, and that its threshold and nonce are correct. The proposer named `pkGARDEN` uses the local `~/.foundry/keystores/pkGarden` keystore; verify its address and Safe Transaction Service proposer/delegate authorization. A proposer need not appear in `getOwners()`. Never expose the key or keystore password.

Once tests, storage review, rehearsal, and final payload review are complete, present the exact ordered files, target chain, transaction count, resolved Safe, proposer, and expected effect to the user. **Ask for explicit approval to submit these specific payloads to the Safe Transaction Service.** Submission creates pending Safe transactions; it does not execute them. Do not submit before that approval. After approval, recheck owner, payload hashes, and nonce; if these changed, stop and obtain approval for the revised plan. Otherwise use `scripts/submit_safe_payloads.py` with `--safe <resolved-safe>`, `--keystore ~/.foundry/keystores/pkGarden`, `--service-chain <chain>`, and repeated `--payload-file <ordered-file>` arguments. Select nonce behavior deliberately (`--skip-pending` unless the approved plan says otherwise). Report the Safe transaction links and distinguish submitted, executed, and verified on-chain states.

## Maintain the network address book

After each transaction **executes successfully onchain**, reconcile only the fields it actually activated in `pkg/contracts/config/networks.json`. Do not promote an address on deployment, fork rehearsal, Safe submission, or an unconfirmed transaction. Compare live reads and receipts with the candidate deployment manifest before editing:

- Factory proxy `upgradeTo`: set `IMPLEMENTATIONS.REGISTRY_FACTORY` to its ERC1967 implementation slot.
- `setStrategyRelease` / `setCommunityRelease` or their implementation-only variants: set `IMPLEMENTATIONS.CV_STRATEGY` / `IMPLEMENTATIONS.REGISTRY_COMMUNITY` to the factory's live core address. Set affected `FACETS` from the factory's complete live cuts, including unchanged selectors; never copy every deployed candidate into `FACETS`.
- Community and strategy template switches: set `IMPLEMENTATIONS.REGISTRY_COMMUNITY_ROUTER` / `IMPLEMENTATIONS.CV_STRATEGY_ROUTER` to the corresponding live factory template after checking `routingFactory()` and family. A router key describes the template; also verify each existing proxy's ERC1967 slot as its migration or router upgrade executes.
- Per-proxy migrations only change `PROXIES` inventory when new instances appear. Re-run the required proxy sync and event reconciliation before declaring the migration complete. Keep `ENVS` proxy addresses unchanged unless their own proxy transaction executed.

Remove or update each promoted `CANDIDATES` entry so it cannot be mistaken for a later release. Preserve the deployment manifest and transaction hashes. Compare the `networks.json` diff against the executed receipts, then run `bash scripts/verify-all-deployments.sh --scope state --network <chain>` and the routed verifier after the full migration or release. The state verifier expects both router templates once shared routing is active, so do not treat a failure during the intermediate migration phases as proof of a bad config; check the live fields activated by that phase directly and run full verification when both families are routed. Commit the reconciled config with the migration or release record.
